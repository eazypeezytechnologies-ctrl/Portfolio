## Challenges We Have Faced

Building this ecosystem has required more than adding features.

### 1. Establishing a reliable source of truth
Some projects existed in multiple repositories or across different AI-assisted development platforms. That created uncertainty about which version was current. The new direction is one canonical private repository per product, intentional migrations, and public documentation here.

### 2. Moving from prototypes to dependable products
A screen that looks complete is not the same as a production-ready product. We have worked through render loops, black screens, state persistence, broken forms, route problems, backend configuration, and unfinished data connections.

### 3. Data quality and source transparency
SafeBite, OwnOps, EazyAcres, and OMNITAGE all depend on information that can change or vary by location, source, language, or user circumstances. The challenge is not simply retrieving an answer—it is showing where the answer came from, how confident the system should be, and when a user must verify it.

### 4. Security, privacy, and infrastructure separation
Backend keys, database policies, client information, and unpublished logic cannot be treated like demo content. We are strengthening environment-variable handling, Supabase configuration, repository privacy, and the rule that each application should have its own backend project rather than sharing one database.

### 5. Scope control and user guidance
Powerful products can quickly become overwhelming. Testing showed the need for clearer “Start Here” flows, progress steps, explanations, next-best actions, and role-specific paths instead of simply adding more screens.

### 6. Cultural accuracy cannot be decorative
Generic output is not good enough for products dealing with identity, community, history, heritage, or culturally specific audiences. Àrokò, EazyAcres, and OMNITAGE now treat culture and lived experience as product intelligence that affects research, recommendations, confidence, and language.

### 7. Building with limited resources
Platform credits, migration friction, integration costs, and the realities of an early-stage studio required a phased approach. We used local-first prototypes, manual research, staged integrations, and reusable brand/product standards rather than forcing expensive automation too early.

## What These Challenges Changed

- **Clarity before scale:** define the user, problem, and next action before expanding features.
- **Manual-first before AI-first:** prove the workflow and information quality before automating it.
- **Evidence over confidence:** show sources, limitations, and verification steps.
- **Separate systems by product:** independent repositories, backend projects, environments, and ownership.
- **Security from the beginning:** credentials and production data never belong in public documentation.
- **Culture as core logic:** community context must influence how systems research, explain, and recommend.
- **Testing is product work:** confusion, failed saves, and incorrect assumptions are design signals—not side issues.
